# DOCX·PPTX 파일 윤문 지원 구현 계획

작성일: 2026-09-08
기준 커밋: `2675c28` · 현재 제품 버전: 0.2.1 · 목표 기능 버전: 0.3.0
상태: 0.3.0 구현 및 검증. 실제 지원 범위와 검증 결과는 docs/documents.md, docs/releases/0.3.0.md에 기록한다.

## 1. 목표와 기본 결정

웹 포털, portable Windows 앱, Claude·Codex `humanize-kr` 스킬에서 DOCX·PPTX를 읽고, 문서의 구조와 서식을 유지하면서 한국어 텍스트를 윤문한 뒤 **입력과 같은 형식의 새 파일**로 제공한다.

- `보고서.docx` → `보고서-humanized.docx`
- `발표자료.pptx` → `발표자료-humanized.pptx`
- 같은 출력 이름이 있으면 번호를 붙인다. 원본은 덮어쓰지 않는다.
- TXT·MD·붙여넣기는 현재 동작을 유지한다.
- 웹/앱은 실행 PC에 설치·로그인된 Claude 또는 Codex CLI를 선택해서 사용한다. 스킬은 현재 호스트 모델로 수행하고 CLI를 중첩 호출하지 않는다.
- 파일 읽기·저장에 Microsoft Office 설치나 별도 클라우드 변환 서비스를 요구하지 않는다.
- 현재 자동 업데이트 대상인 upstream 엔진과 제품용 문서 어댑터를 분리한다. 문서 처리를 위해 upstream 파일을 직접 수정하지 않는다.

이번 범위는 DOCX/PPTX 입력·윤문·동일 포맷 출력이다. DOC/PPT, PDF, HWP, 매크로 문서, OCR, 슬라이드 재디자인, DOCX↔PPTX 상호 변환은 포함하지 않는다.

## 3. 지원 내용과 보존 정책

문서 내부의 모든 XML 텍스트를 무조건 바꾸지 않는다. 화면에 보이는 편집 대상, 보호된 내용, 이번 버전의 미지원 구조를 분석 결과에서 구분하고 개수·위치를 표시한다.

| 요소 | DOCX | PPTX | 초기 정책 |
|---|---|---|---|
| 본문 문단 | 지원 | 지원 | 문단 경계 보존, 한국어 산문 윤문 |
| 표 셀·중첩 표 | 지원 | 지원 | 행·열·병합·셀 순서 보존, 다른 셀로 이동 금지 |
| 제목 | 지원 | 지원 | 짧은 제목/고유명사 보존 우선, 길이를 늘리지 않는 국소 수정 |
| 텍스트 상자·도형 텍스트 | 지원 | 지원 | 지원되는 DrawingML/VML 텍스트를 위치별로 처리 |
| 그룹 내부 텍스트 도형 | 해당 구조 지원 | 지원 | 그룹/도형 ID·좌표·크기 유지 |
| 글꼴·크기·굵기·색상·밑줄 | 보존 | 보존 | 서식 구간 경계를 보호하며 텍스트만 교체 |
| 글머리·번호·들여쓰기 | 보존 | 보존 | Markdown으로 바꾸거나 산문화하지 않음 |
| 하이퍼링크 | 보존 | 보존 | URL·관계·표시 문자열을 보호 구간으로 유지 |
| 그림·차트·SmartArt·수식·첨부 객체 | 보존 | 보존 | 해당 객체 텍스트는 이번 버전에서 윤문 제외, 제외 위치 고지 |
| 머리글·바닥글 | 보존 | 보존 | 본문과 구분하여 그대로 유지 |
| 각주·미주·인용 출처 | 보존 | 해당 텍스트 보호 | 번호·참조·정의·내용 그대로 유지 |
| 발표자 노트 | 해당 없음 | 보존 | 초기 기본은 윤문 제외, 노트가 유지됨을 표시 |
| 마스터·레이아웃·테마 | 해당 스타일 유지 | 보존 | 공통 템플릿을 수정하지 않음 |
| 애니메이션·전환·오디오·비디오 | 보존 | 보존 | 관련 part/relationship와 도형 ID 유지 |
| 주석·필드·목차·책갈피 | 보존 | 보존 | 필드 코드와 필드 결과를 편집 대상으로 취급하지 않음 |

Word 변경 추적이 남은 문서, 데이터 바인딩/잠금 콘텐츠 컨트롤처럼 편집 계약이 불명확한 구조는 사전 탐지한다. 안전하게 보호 범위를 확정할 수 있으면 그 구간만 보존하고 알린다. 범위가 모호하면 변환 전에 지원 불가 사유를 반환한다. 변경 내용을 임의로 승인하거나 제거하지 않는다.

암호화/암호 보호, 패키지 디지털 서명, 매크로 내용, 손상된 ZIP/XML, 확장자와 실제 형식 불일치는 명시적으로 거절한다. 지원하지 않는 구조만 있어 윤문할 내용이 0개이면 “변환 완료” 대신 “윤문 가능한 텍스트 없음”으로 안내한다.

Strict/Transitional OOXML은 namespace와 relationship type을 명시적으로 구분한다. 기본 요소는 양쪽을 처리하고, 미지의 요소를 무시해서 내용을 지우는 방식은 금지한다. Markup Compatibility의 AlternateContent는 실제로 지원하는 한 분기만 처리해 fallback과 중복 윤문하지 않는다. 양쪽 표현을 일관되게 유지할 수 없는 객체는 보존·고지한다.

## 4. 문서 처리 아키텍처

공통 Python 어댑터를 `engine_runtime/documents/`에 추가하고, 웹·앱·스킬이 같은 추출·편집 검증·내보내기 로직을 호출한다.

```text
원본 DOCX/PPTX
  → 패키지 검사 및 원본 바이트 보관
  → 관계 파일을 따라 문서/슬라이드 순서 해석
  → 문단·셀·도형별 텍스트/서식/보호 범위 manifest
  → 문서용 프롬프트로 블록별 편집 요청
  → source hash·구간·내용·길이 검증 및 필요 시 원문 복원
  → 원본 패키지의 허용된 텍스트 노드만 수정
  → 결과 패키지 재검증
  → 같은 형식의 새 결과 파일
```

### 4.1 구현 방식

- ZIP은 Python `zipfile`, XML은 `lxml.etree`를 사용한다.
- 전체 문서를 새로운 DOCX/PPTX로 다시 만드는 방식 대신, 원본 ZIP의 part들을 복사하고 허용된 XML 텍스트 노드만 수정한다.
- 수정하지 않는 각 part의 **압축 해제된 내용 바이트**는 동일해야 한다. ZIP 압축 결과·파일 전체 SHA가 같을 필요는 없다.
- 수정 XML도 namespace prefix, 관계, 주석, 알 수 없는 확장 요소를 유지한다. 변경 가능한 차이는 허용된 텍스트 노드와 필요한 `xml:space`뿐이다.
- 기본 main part 경로를 문자열로 가정하지 않고 `_rels/.rels`, content types 및 내부 relationship을 해석한다. 슬라이드 순서는 presentation의 ID 목록을 따른다.
- lxml은 외부 엔티티/DTD/네트워크 로드를 명시적으로 끄고 recovery 및 huge_tree를 사용하지 않는다. DTD/엔티티 선언이 있는 문서는 거절한다.

Word는 문단 안에서 같은 서식을 가진 run들에 텍스트가 분산될 수 있고, PowerPoint는 슬라이드·도형·노트 등이 별도 part로 나뉜다. 따라서 평문으로 추출한 뒤 문서 전체를 다시 생성하면 원래 구조를 재현하기 어렵다. [Microsoft WordprocessingML 구조](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document), [PresentationML 구조](https://learn.microsoft.com/en-us/office/open-xml/presentation/structure-of-a-presentationml-document)

lxml 파서 옵션은 라이브러리 기본값에 기대지 않고 고정한다. [lxml 공식 파서 문서](https://lxml.de/parsing.html)

### 4.2 의존성 및 배포 결정

구현 첫 단계에서 현재 Python 3.14.7 x64와 호환되는 lxml Windows wheel을 확인하고, 버전·파일·SHA-256·라이선스를 lock 파일에 고정한다. 빌드 시 내려받아 내장 Python의 전용 라이브러리 디렉터리에 배치하고 `._pth`를 명시적으로 설정한다. 사용자 PC에서는 pip 설치나 소스 컴파일을 실행하지 않는다.

웹 서버에도 같은 의존성 버전을 사용하고 health/preflight에서 문서 처리 가능 여부를 확인한다. 문서 의존성이 없으면 문서 기능만 불가 사유를 알리고 TXT/MD의 정상 사용을 유지한다. 다른 OS의 스킬 설치 지침에는 해당 플랫폼의 고정 의존성 설치 절차를 명시한다.

## 5. 서식과 텍스트의 대응을 유지하는 계약

### 5.1 manifest

각 블록에 다음 정보를 저장한다.

```text
document: schemaVersion, format, sourceSha256, originalName, partHashes
block: id, partName, XML 위치, 문단/슬라이드/도형/셀 위치, 원문 해시
       원문 텍스트, run 매핑, 서식 span, 보호 span, 길이 정책, 순서
batch: blockIds, contextBlockIds, 원문 해시, 시도 횟수
```

- ID는 모델이 만들지 않는다. 어댑터가 생성하며, 원본·manifest·배치 해시를 서로 연결한다.
- Word의 표/본문/텍스트 상자를 중복 추출하지 않는다. 문서 위치는 페이지 번호로 단정하지 않고 문단·표 위치로 표시한다. 실제 페이지 나눔은 렌더러에 따라 달라질 수 있다.
- PPTX의 문맥은 슬라이드·도형 단위로 제공한다. XML 도형 순서를 시각적 읽기 순서라고 단정하지 않고 제목/도형 위치 메타데이터를 함께 준다.
- 모델에는 텍스트·필요한 위치 정보·읽기 전용 주변 문맥만 준다. ZIP·XML·사용자 절대 파일 경로를 편집 대상으로 보내지 않는다.

### 5.2 모델 응답

현재 TXT/MD 응답 `rewrittenText`와 분리해 문서용 schemaVersion=1 계약을 추가한다.

```json
{
  "schemaVersion": 1,
  "batchId": "adapter-generated-id",
  "sourceHash": "expected-hash",
  "blocks": [
    {
      "id": "known-block-id",
      "sourceHash": "expected-block-hash",
      "edits": [
        {"start": 0, "end": 6, "before": "가지고 있다", "after": "있다"}
      ]
    }
  ],
  "warnings": []
}
```

위 값은 계약 형태를 보여주는 예시다. 실제 start/end와 before는 정확히 일치해야 한다. offset 단위는 Python과 맞춘 **Unicode code point**로 고정한다. JS의 UTF-16 인덱스와 혼용하지 않는다.

모든 요청 블록은 응답에 정확히 한 번 존재해야 하며 무수정은 `edits: []`다. 알 수 없는 ID, 누락·중복, 해시 불일치, 범위 오류, 겹치는 edit, 원문 불일치를 거절한다. 모델이 특정 XML 노드나 출력 경로를 지정할 수 없다.

### 5.3 run 보존 알고리즘

1. 같은 서식·같은 의미 컨테이너의 인접 run은 하나의 편집 가능 구간으로 묶을 수 있다. 하이퍼링크·필드·책갈피·주석 경계 등은 넘지 않는다.
2. edit는 단일 편집 가능 구간 안에서만 허용한다. 굵은 숫자나 서로 다른 색상 등 **서식 경계를 가로지르는 치환은 거절**한다.
3. 같은 서식 구간의 여러 텍스트 노드에 걸친 교체는 최초 영향 노드에 새 텍스트를 넣고 뒤 노드의 해당 부분만 비운다. run 속성과 텍스트 이외 자식은 보존한다.
4. 삽입은 위치가 속한 구간의 서식을 상속한다. 서로 다른 서식 구간 사이처럼 상속이 모호하면 재시도하거나 해당 edit를 보류한다.
5. 줄바꿈·탭·필드·그림·구분 기호를 텍스트와 구분한다. 다른 문단·셀·도형으로 문장을 이동하거나 병합하지 않는다.
6. 변경률·내용 검증에서 실패하면 해당 블록을 1회 재시도한다. 다시 실패하면 원문을 유지하고 정확한 문서 위치를 경고한다. 잘못된 문서 대응·패키지 구조는 부분 성공으로 감추지 않고 문서 출력을 중단한다.

형태상 run을 남겼다는 것만으로 서식 보존을 통과시키지 않는다. 서식·하이퍼링크가 적용되는 텍스트 범위와 구조까지 검증한다.

## 6. 문서용 윤문 정책

기존 quick-rules를 읽되 문서 보존 제약을 우선하는 별도 prompt를 둔다.

- DOCX/PPTX의 제목·목록·줄바꿈·표를 장식으로 간주해 삭제하지 않는다. 기존 C/J 계열의 산문화 처방을 구조 문서에 그대로 적용하지 않는다.
- 한국어가 없는 텍스트, 숫자/기호만 있는 셀, 코드·URL·수식·발화 인용·고유명사는 보호한다.
- 슬라이드 제목·짧은 레이블은 보존 우선으로 처리한다. 짧은 구절을 억지로 완결 문장으로 늘리지 않는다.
- 전체 원문 평가는 참고로 제공하되 각 편집 블록의 수치·단위·부호·직접 인용·부정·서법 변화도 확인한다. 한 블록의 손실을 다른 블록의 동일 단어로 상쇄하지 않는다.
- 연구에서 확인한 원본 게이트의 한계 때문에 “원본의 숫자 집합이 같다”만으로 승인하지 않는다. 이 기능에서는 숫자·단위와 연결된 보호 구간 및 짧은 발화 인용을 직접 편집 불가로 둔다. 일반 의미 동치 전체를 코드로 증명한다고 표현하지 않는다.
- 정규화는 비교용 텍스트에 제한한다. 원본 OOXML 전체의 공백·NFC·줄바꿈을 일괄 변경하지 않는다.

배치는 기본 목표 7,000자, 최대 9,000자, 최대 32개 편집 블록으로 구성한다. 단락·셀·도형 경계를 넘어 하나의 결과 문자열로 합치지 않는다. 초과 블록은 문장 경계와 보호 구간을 고려해 하위 범위로 나누며, 안전한 분할이 없으면 보존·고지한다. 매 run마다 모델을 호출하지 않고 여러 블록을 한 배치에서 처리한다. CLI 동시성은 기존 제한을 따른다.

### PPTX 넘침 정책

- 글꼴 크기·도형 크기·좌표·자동맞춤 설정을 임의로 바꾸지 않는다.
- 초기 기본은 텍스트 상자/표 셀의 텍스트 길이를 원문보다 늘리지 않는 정책이다. 제목도 같은 제한을 사용한다.
- 길이 증가가 필요하면 짧게 재시도하고, 해결되지 않으면 원문 블록을 유지한다. PPT 문단의 개수와 명시적 줄바꿈은 보존한다.
- 글자 수가 같아도 글자 폭·폰트·환경에 따라 줄바꿈이 바뀔 수 있으므로 이것을 시각적 넘침 검출이라고 주장하지 않는다.
- 릴리스 검증에서는 실제 렌더링으로 넘침·잘림을 확인한다. 제품 런타임은 Office 없이 동작하므로 결과에 “슬라이드 배치 확인 필요” 안내를 제공한다. DOCX도 텍스트 변화에 따른 자연스러운 페이지 흐름 변경을 허용하며 픽셀 동일성은 약속하지 않는다.

## 7. 웹·앱·스킬 연결

### 7.1 웹 포털

기존 `/api/transform`은 평문 경로로 유지하고 문서용 라우트를 추가한다.

1. `POST /api/documents`: 원본 바이너리를 제한된 크기로 스트리밍 수신하고 분석한다. 파일명은 표시용 메타데이터이며 서버 저장 경로로 쓰지 않는다. 문서 핸들·권한 토큰·포맷·편집/보존/미지원 구간 수를 반환한다.
2. `POST /api/documents/:id/transform?engine=...`: 해당 핸들을 기존 작업 큐에 제출하고 NDJSON 진행 이벤트를 반환한다.
3. 완료 이벤트에 `artifactId`, 이름, MIME, 크기, SHA-256, 편집·보존·복원 수, 경고를 제공한다. 바이너리를 `result-delta`나 base64 대형 JSON으로 보내지 않는다.
4. `GET /api/documents/:id/result`: 권한 토큰을 검증하고 검증 완료 파일만 다운로드한다. 프론트엔드는 Authorization 헤더를 포함한 fetch로 받아 Blob 다운로드를 만든다.
5. `DELETE /api/documents/:id`: 취소/화면 초기화 시 해당 작업의 원본·결과·토큰을 정리한다.

권한 토큰은 추측 불가능한 작업별 capability로 발급하고 URL 쿼리·로그에 기록하지 않는다. 다른 LAN 사용자가 job ID만으로 파일을 읽을 수 없도록 한다. Origin 정책과 기존 주소 제한도 적용한다.

사전 업로드와 완료 결과는 마지막 사용 후 30분 TTL로 정리한다. 진행 중인 작업은 TTL 삭제 대상에서 제외한다. 취소·실패는 즉시 정리하며, 다운로드 진행 중인 파일은 잠금을 두어 삭제하지 않는다. 초기 버전은 서버 재시작 시 자기 소유의 남은 문서 작업만 정리하고 재개를 지원하지 않는다. 업로드·결과 보관도 디스크 quota와 최대 대기 작업 제한에 포함한다.

### 7.2 Windows 앱

- 네이티브 파일 선택에서 txt/md/docx/pptx를 제공한다.
- DOCX/PPTX는 main이 파일을 선택·등록하고 renderer에는 불투명한 document handle과 미리보기만 전달한다.
- worker는 등록된 핸들의 원본 복사본만 처리한다. renderer의 임의 절대 경로를 신뢰하지 않는다.
- main의 저장 대화상자로 검증된 artifact를 새 경로에 복사한다. 원본 선택 경로와 같은 경로 또는 기존 파일을 묵시적으로 덮어쓰지 않는다.
- 결과 파일은 저장/새 작업/종료까지 유지하고, 작업용 폴더와 보관 파일을 분리한다. 저장 대화상자 취소 시 결과는 다시 저장할 수 있게 유지한다.
- CLI 선택, 취소, 상태 점검, 앱 종료 시 자식 프로세스 정리는 기존 정책을 재사용한다.

### 7.3 Claude·Codex 스킬

- `humanize-kr` 설명과 workflow에 DOCX/PPTX를 추가한다.
- Gateway의 prepare에서 포맷을 판별하고 TXT/MD는 현재 경로, DOCX/PPTX는 새 문서 경로로 보낸다.
- next는 문서용 응답 스키마·블록 목록·프롬프트/규칙 경로를 반환한다. 호스트가 현재 모델로 JSON 편집 응답을 생성한다.
- accept가 ID·해시·편집 범위·내용·서식을 검사하며 finalize가 원본 패키지에 반영하고 재검증한다.
- 기본 출력 이름은 입력 확장자를 유지한다. finalize의 원본 덮어쓰기 금지와 기존 파일 충돌 방지를 유지한다.
- DOCX/PPTX를 다른 도구로 평문화하거나 새 문서로 재생성해 Gateway 검증을 우회하지 않도록 지침을 명시한다.
- 스킬 ZIP과 설치된 Claude/Codex 사본에 새 어댑터·XML 의존성·문서 workflow가 포함되어야 한다.

### 공통 화면

파일을 고르면 이름·형식·문단/슬라이드 수·윤문 가능한 텍스트 양과 제외 구간을 보여준다. 문서 미리보기는 위치별 텍스트 비교이며 Word/PowerPoint의 실제 페이지 미리보기로 표시하지 않는다. 초기에는 추출 텍스트를 UI에서 직접 편집하지 않는다. 변환 버튼은 분석 완료와 선택 CLI 준비가 모두 끝났을 때 활성화한다. 결과에는 같은 형식 다운로드와 변경/보존/복원 요약을 제공한다.

## 8. 패키지 무결성 및 자원 제한

- 확장자, ZIP 구조, `[Content_Types].xml`, root relationship, 실제 main part의 형식을 함께 확인한다.
- 압축 파일 기본 최대 50 MiB, 해제 합계 250 MiB, entry 10,000개, 단일 XML 10 MiB, 추출 텍스트 100,000자, PPTX 200슬라이드로 시작한다. 초과 시 모델 호출 전에 제한 사유를 반환한다. 수치는 config에 모으고 실제 fixture 성능 결과로 조정한다.
- ZIP 메타데이터의 크기만 믿지 않고 읽는 동안 실제 해제 바이트 상한을 검사한다. 중복 entry, 경로 탈출, 내부 관계의 패키지 밖 경로, XML DTD/엔티티를 거절한다. 외부 링크는 보존만 하고 네트워크로 읽지 않는다.
- 원본 SHA 및 part 해시는 finalize 직전 다시 확인한다. 결과는 새 임시 파일에 쓴 뒤 구조·텍스트 대응 검증을 통과해야 최종 경로로 공개한다.
- 원본의 비편집 part 집합·내용 해시, relationship 집합, 도형/슬라이드/표 구조, 허용된 XML 변경 범위를 검사한다.
- 임시 파일·로그에 원문 내용을 불필요하게 복제하지 않는다. 오류는 파일명/문서 위치/오류 코드 중심이며 모델 응답 전체를 일반 로그에 기록하지 않는다.

## 9. 구현 순서와 완료 조건

| 단계 | 작업 | 산출물 및 완료 조건 |
|---|---|---|
| 1. 패키지 기반 | lxml 내장 실행 확인, OPC/ZIP 검사, fixture 수집, 공통 manifest | Office 없는 환경의 내장 Python에서 import·DOCX/PPTX 분석 성공, 무수정 round-trip 구조·part hash 통과 |
| 2. DOCX | 본문·표·지원 텍스트 상자 추출, run/보호 구간 매핑, 편집 반영 | 혼합 서식·표·그림·인용·각주 fixture에서 지정 텍스트 외 변경 없음 |
| 3. PPTX | 슬라이드 순서, placeholder/그룹/표, 제목·길이 정책 | 슬라이드 수·도형 ID·좌표·테마·미디어·효과 보존, 넘침 사례는 재시도/보존 처리 |
| 4. 실행 계약 | 문서 배치 prompt/schema, TypeScript document engine, Gateway 문서 분기 | Claude/Codex runner 및 두 스킬이 동일 문서 검증 정책 사용, 잘못된 모델 응답으로 파일 생성 불가 |
| 5. 제품 연결 | 웹 바이너리 API·결과 저장소, 앱 문서 IPC, 공통 UI | 업로드→미리보기→변환→동일 포맷 저장, 취소/재시도/TTL/저장 취소 정상 |
| 6. 배포 검증 | 버전·문서·updater 검증 단계 갱신, portable EXE/스킬 ZIP 생성 | DOCX/PPTX 회귀 및 실제 CLI 검사, 새 EXE 자체서명·해시·스킬 설치 확인 |

단계 1에서 의존성 wheel 또는 OOXML round-trip 보존에 문제가 있으면 그 기반을 해결한 후 다음 단계로 간다. 평문으로 바꾸어 출력하면서 DOCX/PPTX 지원을 완료했다고 처리하지 않는다.

### 예상 파일 구성

```text
engine_runtime/documents/

  model.py            manifest/블록/편집 응답 계약

  pptx.py             PowerPoint 추출·텍스트 반영
  edits.py            offset/run/보호 범위 매핑
  validate.py         내용·XML 변경 범위·part 보존 검사
  cli.py              inspect/prepare/accept/export 진입
src/documents/
  document-engine.ts  기존 CLI runner/큐를 이용한 문서 배치 실행
  python-adapter.ts   공통 Python 문서 CLI 호출
  artifact-store.ts   핸들·권한·수명·파일 제공
  routes.ts           문서 API
```

파일명은 구현 중 기존 추상화에 맞춰 조정할 수 있으나, 포맷 처리와 내용 검증은 Python 한 곳을 공유한다. 기존 runner의 프로세스 실행·로그인·취소 로직은 재사용하고 문서별로 복제하지 않는다.

## 10. 검증 계획

### 자동 검증

- DOCX: 서로 다른 run 서식, 표/중첩표/병합셀, 하이퍼링크, 각주·미주·목차·필드·책갈피, 머리글·바닥글, 한글+영어+이모지, 텍스트 상자, 수정 추적/콘텐츠 컨트롤 보호.
- PPTX: 제목·본문 placeholder, 그룹 도형, 여러 run, 표·병합셀, 줄바꿈·글머리, 숨김 슬라이드, 발표 노트, 마스터·테마·그림·차트·SmartArt·효과 보존.
- 구조: 무수정이면 part 내용 완전 동일, 수정 시 허용된 텍스트 외 semantic XML diff 없음. unknown extension namespace도 fixture로 보존 확인.
- 응답: 누락·중복 ID, 잘못된 hash/offset/before, 겹치는 편집, 보호 구간 침범, XML처럼 생긴 사용자 텍스트가 실제 노드로 삽입되지 않는지.
- 의미: 숫자 대상 교환·단위/부호 변경·짧은 인용 변경·당위/추측/부정 변화 등 직전 연구의 반례를 문서 fixture에도 적용.
- 운영: 손상/암호화/위장 파일, ZIP bomb·DTD·경로 탈출, 용량 초과, timeout·취소·프로세스 종료·다운로드 중 TTL·다른 작업 토큰 거부.
- TXT/MD 기존 회귀, 웹 Playwright, packaged Electron Playwright, Gateway 및 스킬 패키지 검사.

### 실제 프로그램·시각 검증

- 실제 Word와 PowerPoint 또는 검증용 LibreOffice에서 결과를 열어 복구 경고가 없는지 확인한다. 대상 Office 호환성을 선언하기 전에는 Word/PowerPoint에서 직접 확인한 결과를 남긴다.
- DOCX는 페이지 렌더링, PPTX는 슬라이드 렌더링으로 잘림·도형 밖 넘침·표 깨짐·서식 손실을 확인한다. 렌더러는 검증 도구이며 portable 제품의 실행 의존성으로 추가하지 않는다.
- 기본/혼합 서식 fixture는 전 페이지·슬라이드를 검토한다. 긴 문서는 변경 위치와 경계 페이지/슬라이드를 포함한다. QA 환경의 폰트도 기록한다.
- 실제 로그인된 Claude와 Codex 각각에서 DOCX 1개·PPTX 1개를 처리한다. 앱 배포본·웹·스킬 연결도 각 경로에서 확인한다. mock 통과를 실제 CLI 검증으로 대신하지 않는다.
- 내장 Python과 XML 라이브러리가 포함된 최종 EXE/ZIP을 사용해 Office·별도 Python 설치 없이 추출·변환·저장을 확인한다.

### 최종 인수 기준

1. 네 경로(웹, Windows 앱, Claude 스킬, Codex 스킬)에서 DOCX/PPTX를 입력하고 같은 포맷으로 저장할 수 있다.
2. 원본 파일은 바뀌지 않고, 문서 구조·서식·비편집 part 보존 검증을 통과한다.
3. 제외·복원·지원 불가 요소는 위치와 함께 고지하고 조용히 삭제하지 않는다.
4. 결과는 실제 Office에서 복구 경고 없이 열리며 대표 fixture의 시각 검증을 통과한다.
5. 기존 TXT/MD 기능과 CLI 선택·로그인·취소 동작이 회귀하지 않는다.
6. `HumanizeKR-0.3.0-win-x64-self-signed.exe`와 Claude/Codex 스킬 ZIP, SHA-256, 릴리스 문서가 함께 준비된다.

## 11. 업데이트 스킬 반영

`update-humanize-engine`의 검증 절차에 DOCX/PPTX 대표 fixture·패키지 의존성 검사를 추가한다. upstream 규칙이 목록 산문화·인용·제목 처리 정책을 바꾸어도 문서 보존 제약이 우선하는지 검사한다. upstream 동기화 후 새 Python 어댑터와 의존성이 EXE/스킬 ZIP에서 빠지지 않는 것도 확인한다.

이번 변경은 “파일 확장자 2개 추가”를 넘어 구조 문서의 왕복 편집 기능을 도입하므로 제품 버전은 0.3.0으로 계획한다. upstream 버전과 커밋 표시는 실제 동기화 결과를 따르며 임의로 올리지 않는다.

## 구현 시 확정한 보수적 처리

초기 릴리스에서 단일 9,000자 초과 문단은 안전한 범위 대응을 우선해 분할 윤문 대신 원문 보존·경고로 처리한다. 텍스트가 없는 필드 시작/끝 문단을 포함해 복합 필드 범위를 보호하고, 줄바꿈·탭은 보호 문자로 매핑하여 그 사이의 본문은 윤문한다. 참고 이미지 렌더러는 배포 의존성에 포함하지 않는다.
