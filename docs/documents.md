# DOCX와 PPTX 윤문

현재 소스 기준: 2026-10-02, `d9df30e`. 아래는 구현의 지원 범위이며, 이번 문서 갱신에서 Office 실파일 변환이나 배포물 실행 검사를 새로 수행한 결과가 아닙니다. [코드 분석](code-analysis.md) · [서비스 분석](service-analysis.md)

0.3.0부터 웹 포털, Windows 앱, Claude·Codex `humanize-kr` 스킬에서 DOCX·PPTX를 처리합니다. 파일 읽기·저장에 Office 설치는 필요하지 않습니다. Windows 배포물은 Python과 lxml 6.1.3을 포함합니다.

## 사용

웹/앱에서 파일 불러오기를 눌러 DOCX 또는 PPTX를 선택합니다. 문서 위치별 텍스트 미리보기와 윤문/보존 구간을 확인하고 Claude 또는 Codex를 선택해 변환합니다. 완료 후 결과 저장을 누르면 입력과 같은 확장자의 새 파일을 받을 수 있습니다. 미리보기는 실제 페이지·슬라이드 렌더링이 아닙니다.

스킬에서는 `/humanize-kr` 또는 `$humanize-kr`에 파일 경로를 전달합니다. 현재 호스트 모델이 편집하고 Gateway가 서식·내용을 검증합니다. 원본을 덮어쓰지 않으며 기존 결과가 있으면 다른 이름을 사용합니다.

## 보존 범위

본문, 표 셀, 지원되는 텍스트 상자·도형의 한국어 텍스트를 대상으로 합니다. 문단·셀·슬라이드·도형 ID, 글꼴·강조·색상 등 서식, 그림·테마·미디어·관계 파일은 유지합니다. 줄바꿈·탭을 보호하면서 그 사이의 텍스트는 편집할 수 있습니다.

머리글·바닥글·각주·미주·발표자 노트·마스터·차트·SmartArt·수식은 그대로 보존합니다. 하이퍼링크, 필드, 변경 추적, 콘텐츠 컨트롤, 처리하기 어려운 호환 객체는 보호합니다. 일부 객체의 텍스트를 윤문하지 않을 수 있으며 위치별 경고로 알립니다.

숫자·URL·영문 이름·한자·일부 인식되는 한국어 이름 등이 있는 문장은 보수적으로 보호하고 직접 인용도 보호합니다. 서식 경계를 넘거나 부정·당위·추측·수량을 바꾸는 편집, 문단 변경률 50% 이상, PPTX 텍스트 길이 증가는 재시도하며 해결되지 않으면 원문을 유지합니다. 응답 식별 정보나 전체 형식이 잘못된 경우에는 작업을 실패 처리합니다. 이러한 검사는 일반적인 의미 동치 전체의 증명은 아닙니다.

PPTX는 원문보다 길어지지 않게 처리하지만 글자 폭·폰트 차이로 배치가 달라질 수 있으므로 최종 슬라이드를 확인해 주세요. DOCX는 윤문 후 자연스럽게 페이지 나눔이 바뀔 수 있습니다.

## 크기와 파일 제한

작은 파일 하나가 메모리·처리 시간·모델 호출을 크게 쓰지 못하도록, 각 한도는 그 한도가 막는 작업보다 먼저 확인합니다. ZIP 끝 기록은 중앙 디렉터리를 읽기 전에, 선언된 크기는 압축을 풀기 전에, 실제로 푼 바이트는 읽는 동안, XML 노드 수와 중첩 깊이는 트리를 만들기 전에 모든 XML part를 한 번 세어서, 텍스트·문단·구간 수는 블록을 뽑는 동안 확인합니다.

- 파일 50 MiB, 압축 해제 합계 250 MiB, XML part 하나 10 MiB, XML 전체 24 MiB, 내부 파일 10,000개
- 압축률: 압축 해제 합계가 8 MiB를 넘으면 파일 크기의 100배까지
- XML 노드(요소·속성·텍스트·주석·처리 명령) 전체 1,500,000개, 중첩 64단계
- 추출 텍스트 100,000자(웹·앱의 텍스트 입력 한도와 같음), 텍스트 조각(텍스트·줄바꿈·탭) 50,000개, 텍스트가 있는 문단·셀 20,000개, PPTX 200슬라이드
- 모델 호출 구간 60개(구간마다 모델 호출 1번, 재시도 때 1번 더)
- 개별 9,000자 초과 문단은 현재 원문을 보존하고 경고합니다. 긴 문서는 여러 문단으로 구성하면 배치 처리할 수 있습니다.
- DOC/PPT/PDF/HWP, 매크로·서명·암호화·편집 보호 파일은 지원하지 않습니다.

한도를 넘는 문서는 모델을 부르기 전에 거절합니다. 웹·앱·MCP 서버·스킬 Gateway가 모두 같은 코드 `DOCUMENT_TOO_LARGE`와 어느 한도인지 알려 주는 한국어 메시지(예: `텍스트 조각이 너무 많은 문서입니다(50,000개 초과). 문서를 나눠서 다시 시도해 주세요.`)를 보여 줍니다. 웹 업로드는 HTTP 413으로 응답합니다. 한도는 원본에 적용하며, 검증을 통과한 편집으로 결과 텍스트가 조금 늘어난 경우는 저장 전 결과 검증에서 다시 막지 않습니다.

## 임시 파일 수명

웹의 업로드/결과는 작업별 권한 토큰으로 보호합니다. 문서는 올린 뒤 30분, 변환이 끝나면 그때부터 30분 동안 보관하고 정리합니다. 이 시각은 고정이라 문서를 다시 조회하거나 내려받아도 늘어나지 않으므로, 한 클라이언트가 보관 자리를 계속 붙잡을 수 없습니다. 만료되거나 삭제된 문서는 받는 중인 다운로드도 끊고 정리합니다. 초기화·취소·실패 시 해당 임시 문서를 정리합니다. 결과는 만료 전까지 다시 받을 수 있습니다. 서버 재시작 시 임시 문서 작업을 재개하지 않습니다.

웹·앱의 문서 보관소는 준비·완료 상태를 포함해 최대 3개를 보관합니다. 웹에서는 이 보관 한도와 변환 큐의 3건 접수 한도가 별개이며, 변환은 일반 텍스트와 함께 한 번에 1건만 실행합니다. 웹의 삭제 요청은 받는 중인 다운로드를 끊고 문서를 지운 뒤에 응답합니다. 실행 중인 변환과 앱의 저장 읽기 임대는 끝날 때까지 삭제를 미룹니다. 접수 전 모델·CLI·큐 오류로 거절되면 준비한 문서를 유지하지만, 접수 후 실패하면 문서를 다시 선택해야 합니다.

앱은 저장 취소 후에도 결과를 다시 저장할 수 있습니다. 새 파일 선택·초기화·앱 종료·만료 시 임시 파일을 정리합니다. 스킬은 결과를 사용자가 선택한 경로에 저장한 후 Gateway cleanup을 실행합니다. 사용자 원본과 내보낸 결과는 삭제하지 않습니다. 스킬 Gateway의 기본 작업 폴더는 그 사용자만 쓰는 곳(Windows `%LOCALAPPDATA%\humanize-kr-skills`, 다른 OS는 임시 폴더의 `humanize-kr-skills-<uid>`, 권한 0700)이며, 엔진 코드는 작업 상태 파일에 적힌 경로가 아니라 Gateway 자신의 위치나 `--vendor-root`에서만 읽습니다.

## 개발과 검증

`npm run desktop:build`가 고정한 lxml Windows wheel을 SHA-256으로 확인해 내장 Python에 배치합니다. 그 후 `npm run test:documents`로 문서 보존 검사를 실행합니다. 웹 개발에서도 Windows에서는 준비된 내장 Python을 우선 사용합니다. 다른 OS에서는 Python 3.11+에 `pip install lxml==6.1.3`으로 동일 버전을 준비합니다.

- `tests/documents/test_documents.py`: 구조·서식·보호 범위·XML·ZIP·Gateway 검증
- `tests/documents/test_document_limits.py`: 크기·압축률·XML 노드·깊이·텍스트·문단·구간 한도와 `DOCUMENT_TOO_LARGE`
- `tests/integration/documents.test.ts`: 실제 Python + 모의 CLI의 웹 왕복/권한 검사
- `tests/desktop/app.spec.ts`: 앱에서 DOCX/PPTX 열기·저장
- `scripts/verify-skill-packages.mjs`: 설치된 두 스킬에서 내장 Python으로 TXT/DOCX/PPTX 왕복
- `scripts/smoke-documents.mjs`: 실제 로그인된 두 CLI를 사용한 DOCX/PPTX 검사

모델은 문서의 XML이나 바이너리를 직접 편집하지 않습니다. source hash·블록 ID·Unicode code point 범위로 편집을 제안하고, 공통 Python 어댑터가 검증된 텍스트만 원본 패키지에 반영합니다. 검증되지 않은 파일은 내보내지 않습니다.
