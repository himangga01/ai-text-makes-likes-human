# T3 report: what Super Sejong v2 should fix as awkward Korean (어색한 한국어)

## Summary

- **Mechanical awkwardness detectors only find errors in unedited human writing.**
  - Seven norm detectors (spacing, 율/률, fixed misspellings, 이였, 로서/로써, object + passive) fire **17–20 times per 10k characters on KatFish human student essays**. They fire **0.00–0.02 on LLM essays**.
  - On the owner's Naver blog (28 posts, 81,743 characters) they fire **0 times**. Across all agreement detectors the blog produced **one** hit.
  - So for the main use case, the correct v2 result is usually "no edit". This contradicts the 윤문 엔진's built-in 10–25% change-rate target for an A grade.
- **The 윤문 엔진 has no norm layer.** It has no 맞춤법, 띄어쓰기, 호응, 겹말 or 로서/로써 rules (grep count 0 in `quick-rules.md`, `diagnosis-rules.md` and `rewriting-playbook.md`; spacing is explicitly "hold"). Its rulebook is almost entirely about "AI tells". It still ships rules this program already rejected, and it asks the model to restructure rhythm (E-1).
- **Kept rules:** six norm rules and four agreement or awkwardness rules have hand-checked precision of 0.92–1.00. They are meaning-safe and 말투-safe, and can drive span-level edit requests (table in section 4). A second group is hint-only. A third group must be left alone, because professional human prose uses the patterns as much as LLMs do, or more.
- **The writer LLM rarely makes norm errors, but it does make 율/률 errors.** 율/률 errors appear in LLM abstracts at 0.47 per 10k (llama3.1 1.20, gpt-4o 0.38). This suits an "introduced by the rewrite" gate like the shipped josa gate.

**Evidence labels used below:** [M] measured here; [C] cited from a source I opened; [R] my reasoning.

**Limit on precision:** all precision figures are my own hand-checks as the T3 researcher, an LLM. No native-reader panel was involved. For norm rules this is close to objective. For awkwardness and style it is not.

## 5. What the 윤문 엔진 gets wrong or misses

- **Misses the norm layer entirely.** Spacing, 맞춤법, 율/률, 로서/로써, adverb and subject agreement, and 겹말 have no rule. Yet these are the only categories with near-objective, high-precision detection, and they are exactly principle 2's target.
- **Keeps rules this program measured and rejected:** A-1 "에 대해", A-7 "가지고 있다", A-9 "에 의해", A-19 "에서의/으로의", and H-3 / A-16 "이는". Professional human prose uses these as much as LLMs or more.
- **Works against principles 1 and 2 by design:**
  - E-1 asks the model to create long sentences and add short ones in every paragraph (rhythm manipulation, not awkwardness).
  - E-2 maps "~고 있다" to simple tense, which changes aspect.
  - The grading scheme rewards a 10–25% change rate.
- **Generic rulebook, no anchors.** The model gets 50+ rules with no source offsets. Nothing checks afterwards that a flagged span was fixed or that unflagged sentences were left alone.

## 6. Design: span-level edit requests and verification

The prototype is `span_verify.py`. Its demo passes on a good rewrite and catches each failure in a bad one.

**Request format (one per finding):**
- Fields: id, rule, start/end (UTF-16 offsets in the chunk), excerpt, sentence index, `kind` (`replace` | `rewrite_span` | `hint`), and Korean guidance.
- Constraints: keep the sentence's speech level, keep protected tokens (numbers, Latin words, quotes), and no edits outside the request sentences.
- **Preferred output contract:** the model returns `{request id → replacement sentence}`, and the engine applies the patches itself. Collateral edits then become impossible by construction. Full-text output is the fallback.

**Verification after the rewrite:**
1. Align sentences (difflib; replaced pairs matched at a character ratio of at least 0.5).
2. Give each request a status: FIXED (its detector no longer fires on the aligned sentence), UNTOUCHED, STILL_PRESENT, or LOST.
3. Reject a fix if the speech-level class changed or if the protected-token multiset changed. In the demo, "많습니다 → 많다" and "85% → 80%" were both caught.
4. Report a collateral rate: changed sentences that carried no request. Spacing-only differences are counted separately. In the demo, an unrequested "좋네요 → 좋습니다" was caught.
5. Run the existing meaning guards and the josa gate.
6. Add rule-specific success checks. For example, A_WAENYA counts as FIXED only if a reason ending is now present. Deleting 왜냐하면 should be logged separately, because it removes the explicit causal link.

**Deterministic tier:** N01, N02 and N05 can be applied by the engine without the model, and only outside quotes, code and headings. I [R] see no 말투 or meaning risk. Make it a mode flag so the owner can opt out.
