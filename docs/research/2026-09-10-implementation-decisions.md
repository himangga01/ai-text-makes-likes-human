# 구현 중 결정한 사항

승인된 직접 입력 강도·변경 표시 계획을 실행하면서 내린 결정과 그 비용을 기록한다. 기능 검증과 별개로 실제 모델의 추가 속도·변경량 측정은 사용자의 요청에 따라 중단했다.

|순서|결정과 근거|판단이 맞지 않을 때의 비용|
|---|---|---|
|1|승인된 구현을 별도 worktree에서 진행하고, 같은 권한을 다시 묻지 않았다. 완성 전에는 기본 작업 폴더의 소스를 바꾸지 않았다.|최종 통합 시 충돌을 정리해야 한다. 사용자 문서와 기존 실행 파일은 보존한다.|
|2|승인 계획에 실행 도구가 읽을 수 있는 Task 제목을 추가했다. 요구사항 변경이 아닌 작업 구분이다.|계획 문서의 중복 설명을 정리할 수 있다.|
|3|구현 담당자는 한 번에 한 명만 실행하고, 독립적인 읽기 전용 리뷰·검증 준비를 함께 진행했다.|순차 구현으로 대기 시간이 발생할 수 있다.|
|4|초기 강한 변환의 재시도 원인이 문자 변경률 상한이라고 가정하지 않고 확인했다. 금지 상투구와 핵심어 보존 문제를 수정하고 30/50 기준을 유지했다.|엄격한 보존 조건으로 실제 수정량이 작아질 수 있다.|
|5|변환 품질 보완이 남아 있는 동안 독립적인 변경 표시 컴포넌트를 구현했다. 품질이 확인되지 않은 상태를 전체 완료로 보고하지 않았다.|엔진 인터페이스가 바뀌면 표시 연결을 다시 수정해야 한다.|
|6|변경 표시 컴포넌트의 최종 재리뷰와 독립적인 보호 문장 복원 보완을 겹쳐 진행했다. 구현 담당자는 겹치지 않았다.|리뷰에서 공유 인터페이스 문제가 나오면 재작업해야 한다.|
|7|스킬에서 앱의 실제 정책·문장 검증·diff 코드를 재사용하도록 로컬 Node bridge를 선택했다. Python Gateway와 현재 호스트 모델의 역할은 유지한다.|Windows 스킬 ZIP이 커지고, 다른 OS의 새 직접 입력 기능에는 Node가 필요하다. 기존 파일 처리는 별도로 유지한다.|
|8|직접 입력·매우 강하게의 초안이 모든 보존 검사를 통과하고 P1 문체 경고만 받은 경우, 실제 두 번째 호출이 그 초안을 원문과 대조하도록 했다. 첫 초안을 자동 선택하지 않으며 불확실한 응답은 일반 재시도·원문 복귀를 따른다.|두 번째 프롬프트가 길어지고, 보수적 재시도의 의미가 원문에서 새로 시작하는 국소 교정에서 기존 후보의 보수적 검토로 제한적으로 바뀐다. 모든 최종 검사는 유지한다.|
|9|UI 읽기 전용 리뷰와 파일이 겹치지 않는 장문 품질 보완을 함께 진행했다. UI 수정이 필요하면 현재 구현 커밋 뒤에 처리했다.|예상하지 못한 인터페이스 의존성이 발견되면 양쪽을 다시 확인해야 한다. 모든 리뷰를 마친 뒤 배포한다.|

실제 측정 기록과 측정 종료 범위는 [강도 평가 기록](2026-09-10-strength-live-evaluation.md)을 참고한다.
