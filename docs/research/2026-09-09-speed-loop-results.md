# 속도 개선 반복 실험 — 2026-09-09

배포 대상은 0.3.3이다. 설치·로그인된 네이티브 CLI를 사용했고, 사용자 모델 설정이나 추론 수준 기본값을 낮추지 않았다. 측정 → 수정 → 같은 입력 재측정 → 내용·서식 검사 순서로 진행했다.

## 최종 측정

| 입력 | 설정 | 기존 | 최종 | 관측 감소율 |
|---|---|---:|---:|---:|
| 일반 텍스트 567자 | Codex GPT-6 Astra / low | 17.57초 | 14.99초 | 14.7% |
| 같은 일반 텍스트 | Claude Sonnet 5 / low | 13.61초 | 5.28초 | 61.2% |
| 사용자 DOCX 5,415자 | Codex GPT-6 Astra / low | 447.39초 | 81.49초 | 81.8% |
| 사용자 PPTX 720자 | Codex GPT-6 Astra / low | 44.15초 | 17.15초 | 61.1% |

일반 텍스트는 각 설정별 3회 중앙값이다. 기존 Codex는 17.57/16.53/21.93초, 최종은 15.59/14.99/14.19초였다. Claude 기존은 23.43/9.31/13.61초, 최종은 5.27/5.28/5.50초였다. 전부 본문 및 전체 문서 게이트를 통과했고 재시도·원문 복원은 없었다.

문서 기준값은 같은 날 앞서 실행한 동일 파일의 기록이며, 최종 형식은 파일별 1회 측정이다. DOCX 최종 81.49초에는 검증 재시도 1회가 포함된다. 64.67초를 기록한 중간 DOCX 실험도 있었지만 최종 결과 수치와 구분했다. 서버 부하·네트워크·캐시 상태를 통제한 대규모 실험이 아니므로 감소율은 이번 표본의 관측값이다. 장문 일반 텍스트와 다른 모델/추론 수준의 지연 분포는 별도 측정이 필요하다.

## 반영한 변경

1. 일반 텍스트는 전체 본문을 재출력하는 대신 정확한 원문 구절과 치환문을 받는다. 수정할 곳이 많으면 전체 본문 출력도 가능하다. 프로그램이 유일한 원문 일치를 확인하고 결과를 조립한 뒤 기존 복원·검증을 그대로 실행한다. 반복 문구·범위 중복·원문 불일치는 추측해서 적용하지 않는다.
2. Office 입력에서는 서식 SHA와 XML 경로를 모델에 보내지 않는다. 실제 서식 경계·보호 구간 검증에 필요한 원본 메타데이터는 로컬 manifest에 유지한다.
3. Office 배치는 원문 7,000자, 최대 96블록, 직렬화 블록 합계 48,000바이트를 기준으로 나눈다. 한 블록 자체가 예산보다 큰 경우는 기존 블록 길이 상한 내에서 단독 처리한다. 완전히 보호된 텍스트는 호출 대상에서 제외한다. DOCX는 8배치에서 3배치가 됐다. 병렬 호출 수는 늘리지 않았다.
4. Office 응답 v2는 모든 검토 ID를 순서대로 확인하고 편집이 있는 블록만 받는다. 검토 ID가 빠지면 생략 블록을 무수정으로 간주하지 않는다. sourceHash·블록 해시·작업/시도 식별 검사는 유지한다. 이전 v1 응답도 읽을 수 있다.
5. Office v2도 정확한 원문 구절을 기준으로 Python이 Unicode 위치를 계산한다. 모델의 위치 계산 오류를 줄이되, 여러 번 나오는 구절을 임의로 선택하지 않는다. 저장 전 서식·내용·보호 구간·변경률·길이 검사는 유지한다.
6. 데스크톱 일반 텍스트의 IPC 호출 응답이 완료 이벤트보다 먼저 도착하는 경우를 재현했다. 두 응답을 모두 기다리게 수정해 빠른 작업의 결과 누락을 방지한다.

## 반복 과정에서 배운 점

- 텍스트 첫 실험은 중앙값 13.81초였다. 다만 일부 어휘를 덜 고치는 경향을 발견해 모든 문단에 규칙을 적용한 뒤 응답 형식을 선택하도록 보완했다. 보완 후 중앙값은 14.99초다. 모델의 어휘 선택과 수정 개수는 여전히 실행마다 달랐다. 게이트 통과를 동일한 규칙 적용 강도의 증명으로 해석하지 않는다.
- 문서에서 배치만 키우고 무수정 블록까지 전부 출력하게 한 실험은 첫 배치 대기가 길어 중단하고 작업을 정리했다. 입력량뿐 아니라 응답량을 함께 줄여야 했다.
- 검토 ID와 실제 편집만 출력한 DOCX 중간 실험은 64.67초였다. 기존 결과와 ZIP 내부 18개 part가 모두 동일했다.
- PPTX에서 모델 offset 오류로 재시도한 실험은 49.67초로 오히려 느렸다. 위치를 로컬에서 계산하는 최종 형식에서는 17.15초, 재시도 0회였다.
- 최종 DOCX는 반복 구절의 유일성 검사에서 1회 재시도했다. 최종 5블록 수정 중 기존 4블록의 변경과 같은 내용 및 조사·접속 표현 수정 1개를 확인했다. 임의의 최소 수정률이나 검증 완화는 추가하지 않았다.

## 내용·서식과 배포 검증

- 사용자 원본은 덮어쓰지 않았다. 문서 출력 시 변경 part의 허용 텍스트 외 XML 구조와 나머지 part의 바이트 보존 검사를 통과했다.
- 최종 PPTX는 기존 검증 결과와 모든 ZIP part가 동일하다. 최종 DOCX는 Word에서 정상 열리고 PDF 출력도 8페이지를 유지했다. 추가 변경이 있는 페이지를 렌더링해 잘림 없이 유지됨을 확인했다.
- 일반 텍스트는 원문과 결과를 직접 대조했고 사실·부정·유보 표현 보존 게이트도 통과했다. 윤문 품질을 자동 게이트만으로 보장하지 않는다.
- 단위·통합 205개, 문서 Python 28개, 텍스트 스킬 Gateway 3개, 웹 E2E 20개, 최종 패키징 데스크톱 10개로 총 266개 검사를 통과했다. 별도 계정 호출이 필요한 기존 조건부 테스트 3개는 일반 테스트 실행에서 제외되며 위의 실제 CLI 벤치마크를 따로 수행했다.
- Claude Office 실호출도 문서 저장까지 확인했다. 합성 fixture에서 서식 경계·50% 변경률 검사가 재시도 및 2블록 원문 보존으로 작동했다.
- 두 호스트의 스킬 아카이브는 독립 디렉터리에 2회 설치해 멱등성 및 내장 Python TXT/DOCX/PPTX 왕복·정리를 검증했다. 기존 사용자 스킬은 백업 후 갱신한다.
- 최종 0.3.3 portable EXE를 별도 한글 경로로 복사하고 PATH에서 사용자 Node/Python을 제외한 상태로 실행·변환·작업 정리를 통과했다. 이 마지막 배포 smoke는 가짜 CLI를 사용했으며 실제 모델 속도 측정과 구분한다. 자체 서명 EXE SHA256은 `478f0c528a307ec0416552e44a24f2c04e1601a51585b90ebbf7a5bf27b4376b`다. 기존 로컬 인증서로 서명했으며 신뢰 루트는 변경하지 않았다.
- 사용자 문서와 생성 결과는 Git에 추가하지 않는다. 결과는 `test docx pptx/속도 개선 결과-0.3.2/`, 상세 실험은 무시되는 `runtime/test-tmp/speed-loop/`에 있다. 최종 앱 0.3.3은 텍스트 IPC 수정만 추가하므로 문서 결과 형식은 같다.

## 재실행

실제 계정의 CLI를 호출하므로 실행 시 사용량이 발생한다. 보통 3회만 실행하고 실패·품질 회귀가 있으면 수정한 뒤 같은 입력을 재측정한다. 무제한 자동 반복은 하지 않는다.

```powershell
npm.cmd run build
npm.cmd run benchmark:speed -- candidate

$env:BENCH_PROVIDER='claude'  # 기본 codex
$env:BENCH_RUNS='3'
npm.cmd run benchmark:speed -- claude-candidate

$env:BENCH_DOCUMENT='C:\문서\입력.docx'  # DOCX/PPTX는 1회
npm.cmd run benchmark:speed -- document-candidate
```

`BENCH_MODEL`로 모델을, `BENCH_TEXT_FILE`로 일반 텍스트 입력을 지정할 수 있다. 추론 수준은 비교를 위해 low로 고정된 벤치마크 전용 값이다. 앱 설정에는 영향을 주지 않는다. 기준 빌드를 별도 디렉터리에 보관했다면 `BENCH_DIST`와 `BENCH_SCHEMA`로 기준 구현/스키마를 지정한다. 각 라벨의 report.json이 단계별 시간과 호출 수를 기록한다. 같은 라벨은 기존 보고서를 갱신하므로 비교 단계마다 다른 라벨을 사용한다.

숫자만 추린 증거는 [speed-loop-evidence.json](2026-09-09-speed-loop-evidence.json)에 있다. 규칙 적용 강도 메뉴는 이번 속도 변경과 별도이며 이전 연구의 제안 상태다.
