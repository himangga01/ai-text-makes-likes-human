# 문서 윤문 속도와 규칙 적용 강도 검토

검토일: 2026-09-09 · 기준: HumanizeKR 0.3.1 / `a2aff0f`

측정값과 모의 계산은 [집계 증거 JSON](2026-09-09-speed-strength-evidence.json)에 기록했다.

## 결론

**속도를 개선할 구체적인 여지가 크고, 규칙 적용 강도 메뉴도 구현할 수 있다.** 우선순위는 문서 입출력 최적화보다 모델에 주고받는 데이터의 축소와 호출 수 감축이다. 강도는 현재의 모델·추론 레벨과 분리하여 `보수 / 표준 / 적극`으로 제공하는 것이 적절하다.

현재 제품에는 독립적인 윤문 강도 옵션이 없다. 기존 `low/medium/high/...`는 CLI의 추론 effort이며, 얼마나 적극적으로 문장을 바꿀지 정하는 편집 정책이 아니다. 강도를 올려도 모델·effort를 자동으로 바꾸지 않는 설계를 권한다.

이번 작업은 코드 검토, 이전 실제 실행 증거 분석, 기록된 응답을 이용한 로컬 재생 실험, JSON 경량화 모의 계산이다. 제품 코드나 옵션 메뉴는 아직 변경하지 않았으며, 최적화·강도별 새 LLM A/B 실험도 실행하지 않았다.

## 1. 실제 실행과 추가 측정

사용자가 제공한 최근 DOCX/PPTX 테스트를 기준으로 삼았다. 실제 모델은 Codex GPT-6 Astra / low였다. 사용자 문서 본문은 이 검토 문서에 복제하지 않는다.

| 항목 | PPTX | DOCX |
|---|---:|---:|
| 원문 분량 | 720자 | 5,415자 |
| 문서 크기 | 1슬라이드 | 8페이지 |
| 추출 블록 | 17 | 242 |
| 현재 editable로 분류한 블록 | 16 | 241 |
| 실제 모델 호출 배치 | 1 | 8 |
| 변경한 블록 | 4 | 4 |
| 무수정 응답 블록 | 12 | 237 |
| 재시도 / 원문 복원 | 0 / 0 | 0 / 0 |
| 실제 변환 소요 | 44.146초 | 447.394초 |

모델에 보내지 않아도 되는 완전 보호 구간이 editable 목록에도 들어 있었다. 보호 범위 합집합이 공백을 제외한 전체 문자를 덮는지 계산하면 PPTX 1개, DOCX 20개다. 모델에게 전송되지만 실질적으로는 편집할 수 없는 블록이다.

DOCX에는 20자 이하 블록이 143개, 중복된 텍스트가 16개 있었다. 단, **짧거나 중복된다는 이유만으로 일괄 제외해서는 안 된다.** 짧은 문장에도 번역투가 있을 수 있고 같은 표현도 위치에 따라 역할이 다르다. 제목·표 헤더·날짜·고유명사 같은 구조적 역할과 규칙 후보 여부를 함께 판단해야 한다.

### 모델을 제외한 전체 경로 재생

이전 실행의 승인된 편집 응답을 재사용해 `prepare → accept(배치별) → finalize → cleanup`을 실제 내장 Python 프로세스로 3회 실행했다. 새 모델 호출은 없었다. 임시 출력은 별도 테스트 디렉터리에 만들었고 원본은 수정하지 않았다.

| 포맷 | 1회 | 2회 | 3회 |
|---|---:|---:|---:|
| PPTX, 1배치 | 404.4ms | 402.4ms | 401.8ms |
| DOCX, 8배치 | 1,244.3ms | 1,263.9ms | 1,240.9ms |

순수 모듈 호출로 추출·내보내기 검증만 측정하면 DOCX는 약 0.20초였다. 프로세스 실행과 배치별 Gateway 왕복을 포함해도 위 재생은 약 1.25초다. 이 실험은 warm local 환경이며 실제 LLM의 프로세스 기동·네트워크·입력 처리·추론·출력 생성 시간을 개별 분리한 프로파일은 아니다. 따라서 지연의 정확한 비율을 특정 단계에 귀속하지 않는다. 다만 7분 27초의 주된 병목이 XML 파싱·ZIP 저장이라는 설명은 측정과 맞지 않는다.

## 2. 느린 이유

### 2.1 본문 길이보다 32블록 제한이 호출 수를 결정한다

현재 `extract()`는 원문 7,000자 또는 32블록마다 배치를 끊는다. 이번 DOCX는 총 5,415자여서 문자 기준으로는 한 묶음에도 들어가지만, 실제 배치는 `[32,32,32,32,32,32,32,17]`이었다. 표의 짧은 셀과 제목도 각각 한 블록이다. [배치 구성](../../engine_runtime/documents/model.py)

그 배치를 `DocumentEngine.transform()`의 while 루프에서 하나씩 처리한다. semaphore도 1이며 Gateway는 단일 `current/attempt` 상태를 사용한다. 즉 8번이 모두 순차 실행된다. [문서 엔진](../../src/documents/document-engine.ts) · [Gateway 상태](../../engine_runtime/documents/workflow.py)

### 2.2 본문보다 메타데이터가 크다

현재 `public_block()`은 모델에게 원문 외에 블록별 SHA-256, 위치, 서식 span, 보호 범위, 길이 제한을 보낸다. 특히 `spans.style`에는 해시와 XML 경로가 들어가는데, 모델은 서식의 동일성 판정이나 XML 위치 복원을 직접 수행하지 않는다. 이 값은 로컬에 둘 수 있다.

동일한 저장 manifest를 표준 JSON으로 재구성한 문자 수는 다음과 같다. **토큰 수나 청구량이 아니라 Unicode 문자 수**다.

| 항목 | PPTX | DOCX |
|---|---:|---:|
| 배치 입력 JSON 합계 | 6,569 | 83,990 |
| 매 호출에 포함되는 quick-rules | 8,489 | 8,489 |
| 반복 포함한 규칙집 합계 | 8,489 | 67,912 |
| 전체 응답 블록을 재구성한 JSON | 1,972 | 26,890 |

DOCX에서는 입력 JSON과 반복 규칙집만 합쳐 약 15.2만 문자다. 원문은 5,415자인데 이를 처리하기 위한 표현이 지나치게 크다. 규칙 파일의 로컬 읽기는 이미 Promise로 캐시되지만, 프롬프트에는 호출마다 포함된다.

반복 전송이 곧 매번 모델의 cache miss를 뜻하지는 않는다. 현재 실행의 cache hit/token 사용량은 기록하지 않았으므로 확인할 수 없다. Claude의 공식 설명에서도 prefix caching은 입력 처리에 도움이 되지만 출력 생성 자체를 줄이지는 않는다. 따라서 무수정 JSON 출력을 줄이는 일은 캐시 여부와 별도로 유효한 개선 방향이다. [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) · [Claude Code의 캐시](https://code.claude.com/docs/en/prompt-caching)

### 2.3 수정하지 않은 237개도 긴 결과로 반환한다

현재 스키마는 모든 요청 블록에 대해 `id + sourceHash + edits`를 반환하도록 한다. 이 문서에서는 4개만 수정했지만 나머지 237개의 해시와 빈 배열도 모델이 출력했다. 변경이 적을수록 이 비용의 비중이 커진다.

같은 승인된 편집을 다음 형태로 재직렬화하면 약 26,890자에서 2,303자로 **91.4% 감소**했다.

```text
batchId + inputDigest
reviewedIds: 검토한 모든 요청 블록의 짧은 ID
changes: 실제로 수정한 블록의 edit만
```

이 수치는 제안된 응답 구조의 크기를 계산한 결과다. 실제 모델의 토큰 수·시간·정확도가 91.4% 개선됐다는 뜻은 아니다.

## 3. 속도 개선 우선순위

| 순서 | 개선 | 기대 효과와 조건 |
|---|---|---|
| 1 | 모델 응답은 검토 ID + 실제 변경분만 반환 | 무수정 블록의 해시·빈 배열 생성 제거. 원문/배치 digest와 ID 완전성 검증 유지 |
| 2 | style 해시·XML 경로·중복 블록 해시는 로컬에 보관 | 모델에는 짧은 ID·텍스트·숫자 범위·길이 제약만 전달. 후보 축소 없이도 입력을 줄임 |
| 3 | 완전 보호 구간을 전송 후보에서 제외 | DOCX 20개는 확실한 낭비 제거 대상. 미검토 문장 누락과 구별해 coverage 기록 |
| 4 | 32개 고정 제한을 완화하고 직렬화 크기 예산으로 배치 | 사례상 cap 64→4회, 96→3회, 128→2회. 7,000자만 보고 무조건 한 호출로 보내지 않음 |
| 5 | 독립 배치를 최대 2개 병렬 처리 | 추가 wall-clock 감소 가능. 순서 무관 accept, 배치별 상태·lock·취소·재시도부터 구현 필요 |
| 6 | 반복 셀·짧은 표 헤더를 구조적으로 분류 | 문맥 없는 중복 제거를 피하고 확실한 레이블만 보존. 적극 모드의 규칙 후보까지 제외하지 않음 |
| 7 | 단계별 계측, 캐시와 모델별 비교 | CLI 전체 시간·TTFT·출력량·재시도 원인·배치별 소요를 남겨 후속 최적화 판단 |

완전 보호 구간과 style 해시를 제외한 입력 구조를 모의 계산하면 DOCX 배치 데이터가 83,990자에서 29,040자로 줄었다. 이 값 역시 실제 새 프롬프트의 품질·속도 검증을 대신하지 않는다.

권장 첫 목표는 **이 사례의 8회 호출을 2~3회로 줄이고, 무수정 결과의 긴 출력을 없애는 것**이다. 병렬화는 그 다음이다. “7분을 반드시 몇 초로 줄인다”는 약속은 현재 자료로 할 수 없다. JSON 크기 감소, 입력 처리 시간, 모델 추론량, 서비스 부하가 각각 다르게 작용한다.

### 반드시 유지할 검증

- `reviewedIds`가 요청 후보 ID 집합과 정확히 일치해야 한다. 누락을 무수정으로 몰래 처리하지 않는다.
- batch ID와 원문 digest를 대조하고, 모델이 보내지 않는 per-block 해시·XML 위치는 로컬 manifest에서 검증한다.
- 변경 ID가 검토 목록의 부분집합인지 확인하고 중복·겹치는 편집·잘못된 offset을 거절한다.
- 배치 병렬화에서도 같은 블록이 두 배치에 배정되지 않아야 한다. 전체 조립은 모든 배치 검증 후 실행한다.
- 모델 입력 축소는 규칙집 전체 삭제나 의미 보존 검사 제거로 달성하지 않는다.

### 우선순위가 낮은 작업

Python을 다른 언어로 다시 구현하기, ZIP 압축 설정 미세 조정, next 응답의 미리보기 캐시 등은 현재 1.25초 구간을 줄이는 작업이다. 주 병목을 먼저 해결한 뒤 고려한다. 영구 CLI 세션도 프로세스 기동 시간이 유의한 병목임을 측정한 뒤 검토한다. 새 프로세스라고 캐시가 반드시 없어지는 것은 아니다.

## 4. 지금 수정이 적은 이유

이번 두 문서에서는 재시도와 원문 복원이 없었다. 따라서 “모델이 많이 고쳤는데 검증기가 대부분 되돌렸다”는 설명은 이번 실행에 맞지 않는다. 모델이 DOCX 237개, PPTX 12개 블록을 처음부터 무수정으로 반환했다.

현재 문서 프롬프트는 “국소 윤문”, “서식·내용 보존이 불확실하거나 필요 없으면 edits: []”를 강하게 지시한다. 수치가 있는 문장은 전체 보호하고, 서로 다른 run 서식 경계를 가로지르는 편집을 거절하며, PPTX는 길이가 늘면 거절한다. [문서 프롬프트](../../src/engine/document-prompt.ts) · [편집 검증](../../engine_runtime/documents/model.py)

실제 변경도 대부분 연결어미 뒤 쉼표 제거였고 DOCX의 한 표현만 간소화됐다. 이는 모델이 보수적인 편집을 선택했다는 관측이다. 다만 그 사실만으로 원문에 다른 고칠 표현이 전혀 없다고 판단할 수는 없다. 규칙별 탐지·적용·보류 이유를 현재 응답에 기록하지 않아 추가 분석이 필요하다.

현재 앱이 읽는 것은 전체 taxonomy가 아니라 quick-rules 61개다. 추론 effort를 올린다고 전달하지 않은 규칙이나 문서 구조 편집 권한이 새로 생기지는 않는다. 강한 모드의 범위도 실제 로드한 규칙과 포맷별 보존 제약에 맞춰 정의해야 한다.

## 5. 적용 강도 메뉴 설계

**구현 가능하다.** 다만 “몇 % 바꿀지” 슬라이더보다는 사용자가 결과 차이를 이해할 수 있는 3단계가 적절하다.

| 강도 | 의도 | 허용하는 편집 범위 |
|---|---|---|
| 보수 | 원문 유지 우선 | 확실한 번역투·불필요한 반복·부호를 최소 수정. 불확실하면 유지 |
| 표준 | 자연스러움과 보존의 균형 | 규칙의 문맥·빈도 조건을 충족하는 표현을 폭넓게 점검하고 구·서술어를 다듬음 |
| 적극 | 번역투·상투적 문장 틀을 더 적극적으로 완화 | 동일 문단·서식 범위 안에서 문장 내부 구조·명사화·반복·수사를 재구성. 변화마다 규칙 근거를 요구 |

단계별 차이는 프롬프트 한 단어가 아니라 **판정 기준, 처방 범위, 보류 정책, 규칙별 적용 기록**으로 만든다. 규칙의 원래 문맥 조건을 없애 모든 표현을 금지어처럼 취급하지 않는다. 예를 들어 “~를 통해”가 자연스러운 한 번의 사용이면 적극 모드에서도 무조건 삭제할 이유가 없다.

### 추론 레벨과 구분

- 모델: 어떤 모델이 편집하는가.
- 추론 레벨: 모델이 판단에 어느 정도 자원을 쓰도록 요청하는가.
- 규칙 적용 강도: 어떤 문체 문제까지 손대며 얼마나 재구성하는가.

`적극 + low` 또는 `보수 + high`도 유효한 조합이다. 높은 effort는 시간·토큰 사용을 늘릴 수 있지만 편집량을 보장하는 설정은 아니다. 이미 느렸던 최근 테스트도 low였다. [Claude effort 공식 설명](https://platform.claude.com/docs/en/build-with-claude/effort)

### 모든 강도에서 고정할 항목

수치·단위·대상 관계, 날짜·회사/사람 이름, 직접 인용, 긍정/부정, 의무/요구/유보의 의미, 제목·표·슬라이드·run 서식 구조를 보존한다. PPTX 도형·글꼴 크기를 임의로 바꿔 긴 문장을 끼워 넣지 않는다. 적극 모드도 문서 재디자인 기능이 아니다.

현재 블록 변경률 50% 중단을 강도라는 이유만으로 바로 해제하는 방식은 권하지 않는다. 짧은 문장에서는 자연스러운 교정도 50%를 넘을 수 있으므로, 적극 모드의 거절 원인을 먼저 계측하고 별도로 보정해야 한다. 같은 맥락에서 `MODAL` 정규식의 완전 일치 검사도 안전한 바꿔쓰기를 거절할 수 있다. 강한 편집을 허용하려면 이런 판정의 한계와 실제 의미 변경을 구분해야 한다.

TXT/MD에서는 기존 연구에서 확인한 숫자 대상 교환·짧은 인용·부정 반전의 검증 공백도 함께 회귀 검사한다. 강도를 올리면서 검증이 의미 보존을 완전히 보장한다고 표현하지 않는다.

## 6. 옵션을 연결할 위치

웹·Windows 공통 화면에 `규칙 적용 강도: 보수 / 표준 / 적극`을 추가하고 모델·effort와 별도로 저장한다. 작업 시작 시 선택값을 고정하며 완료 요약에도 실제 사용한 강도를 표시한다.

- `public/app.js`, transport, document-file: 선택·저장·요청 전달.
- API/IPC: enum 검증. 요청별 상태로 전달해 다른 사용자의 대기 작업에 섞이지 않도록 한다.
- `PromptInput` 및 일반/문서 프롬프트: 동일 강도 프로필을 공유하고 문서 포맷의 구조 보존 지시를 우선한다.
- Gateway manifest/batch: 옵션·원문 digest를 작업에 결합한다. 모델이 응답에서 강도를 바꿀 수 없도록 한다.
- 스킬: 같은 옵션을 natural language/CLI 인자로 전달하고 같은 검증 정책을 사용한다.
- 재시도: 검증에 통과한 편집은 보존하고 실패 블록/편집만 재검토하는 방향으로 바꾼다. 적극 요청을 전체 보수 모드로 무조건 덮어쓰지 않는다.

초기에는 강도만 새 메뉴로 추가하고 속도 최적화는 내부에서 자동 적용하는 구성이 단순하다. 별도의 “빠름/정밀” 메뉴까지 동시에 늘리면 추론 레벨·강도와 의미가 겹칠 수 있다.

## 7. 검증 및 적용 순서

1. **진단 정보 추가:** 배치별 CLI 소요·가능한 token/cache 지표·출력 길이·검증 시간·수정/보류 원인을 기록한다. 원문 전체를 일반 로그에 남기지 않는다.
2. **응답/입력 경량화:** reviewedIds + 실제 changes, 짧은 ID, 로컬 해시·서식 보관. 이때 기존 승인 편집을 그대로 재생해 파일 무결성을 비교한다.
3. **배치 재구성:** 64/96/128 후보를 실제 직렬화 크기 제한과 함께 비교한다. 이 문서에서 8→2~3 호출을 목표로 평가한다.
4. **강도 3단계:** 모델과 effort는 고정하고 세 강도의 규칙 적용률·내용 보존·문서 배치를 비교한다. 효과 없는 이름만의 옵션을 피한다.
5. **필요 시 2개 병렬화:** 순서 무관 commit과 취소·중복·부분 실패 처리를 검증한 뒤 도입한다.

평가 자료는 이미 사용한 두 문서, AI 번역투가 실제로 많은 글, 이미 자연스러운 사람 글을 함께 사용한다. 같은 모델/effort로 반복 실행하고 중앙값·실패·재시도·파일 구조·의미 손실·잔존 규칙을 비교한다. 적극 모드에서 변경률이 반드시 높아야 한다는 최소 수정량 조건은 두지 않는다. 규칙 근거 없는 수정은 개선으로 세지 않는다.

현재 확보한 결과로는 **호출/출력 설계의 비효율과 옵션 구현 가능성은 확인**했다. 최적화 후 실제 처리 시간, 강도별 자연스러움 개선, 포맷별 실패율은 위 A/B 검증을 거쳐 확정해야 한다.
