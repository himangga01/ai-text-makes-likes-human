# 변환 강도별 지원 범위 상세 연구

2026-09-10 · 서비스 0.3.3 / 엔진 2.3.2, `9747f036cdc28a1a8aea4dc71fef1f7846eb96f7` 기준

## 결론

사용자의 추가 요구에 따라 **매우 강하게는 글 전반에서 많은 문장의 표현과 구문을 실제로 재구성하는 모드**로 정의한다. 단순히 검토를 더 꼼꼼하게 하거나 몇 단어만 치환하는 수준으로 완료 판정하지 않는다.

다만 현재 오픈소스는 ‘문제가 있는 구절만 국소 수정’하는 윤문 엔진이다. 네 단계 중 보통은 기존 정책을 유지할 수 있지만, 매우 강하게의 넓은 재서술은 서비스가 확장하는 기능이다. 현재 코드에 옵션 값만 추가한다고 검증까지 완성되는 것은 아니다.

기준 코드를 읽고 직접 작성한 6개 후보 문장쌍으로 결정적 검증을 실행했다. 이 문서의 변환 예시는 **설계 예시**이며 4단계 프롬프트의 실제 모델 실행 결과가 아니다. 새로운 LLM 호출이나 기능 구현은 하지 않았다.

## 1. 강도를 구분할 네 가지 축

1. **편집 범위:** 구절 → 문장 내부 여러 구절 → 문장 구문 → 글 전반의 문장 재서술.
2. **문장 수정 범위:** 눈에 띄는 문제 문장 위주 → 적용 가능한 여러 문장 → 재구성이 유효한 문장 전반.
3. **원래 표현 보존 정도:** 기존 표현을 최대한 유지 → 자연스러운 대안으로 적극 교체. 내용과 사실 보존 정도는 모든 단계에서 동일한 목표다.
4. **보호 제약:** 이름·숫자·인용·주장·서법·시간·조건·인과·핵심 개념어는 강도를 높여도 보호한다.

‘강도 높음 = 정확성 낮아도 허용’, ‘effort 높음 = 많이 고침’, ‘교체 비율이 높음 = 품질 좋음’으로 구현하지 않는다.

## 2. 단계별 제품 정의

| 단계 | 사용자 설명 | 실질적으로 허용할 작업 | 적용 범위 |
|---|---|---|---|
| 보통 `normal` | 원래 표현을 살려 어색한 부분을 다듬습니다. | 현재 룰북의 명확한 번역투·이중 피동·불필요한 쉼표·형식적 구절 등을 국소 교정 | 문제가 확인된 부분 중심 |
| 중간 `medium` | 어휘와 길어진 표현을 더 자연스럽게 정리합니다. | 보통 + 한 문장에 있는 여러 어색한 구절을 함께 교정, 의미 없는 명사화·중복 수식 정리, 국소 주어·서술 연결 개선 | 해당 문제가 있는 문장 안의 여러 부분 |
| 강하게 `strong` | 문장 구조와 반복 표현까지 적극적으로 바꿉니다. | 중간 + 피동/능동 구문 전환, 주어·서술어 관계가 유지되는 어순 재배치, 긴 수식 구조 정리, 반복 구문 변주 | 근거 있는 문제 문장 전체를 재구성 가능 |
| 매우 강하게 `very-strong` | 뜻은 유지하고 글 전반의 표현과 문장 구성을 크게 바꿉니다. | 강하게 + 재서술 가능한 문장 전반을 대상으로 복합 구문·어순·서술 방식·호흡을 새로 구성. 원래 문장 형태를 그대로 남기는 것을 우선 목표로 두지 않음 | **글 전반에서 많은 문장을 실제 변경**. 사실·인용 등 보호 문장은 제외/제한 |

보통에서도 기존 룰북 전체를 검토한다. 특정 오류를 일부러 남겨 상위 단계에서만 고치도록 만들지 않는다. 네 단계는 오류 탐지 수준보다 **허용하는 재구성의 넓이와 표현 보존 우선순위**가 다르다. 짧고 단순한 문장은 여러 단계에서 같은 결과가 나올 수 있다.

### 매우 강하게의 추가 요구 반영

- 모든 편집 가능한 문장을 재서술 후보로 검토하고, 글 전반에서 의미를 보존하는 유효한 대안이 있는 문장을 적극적으로 바꾼다.
- 이미 문법적으로 맞는 문장도 어순·구문·호흡을 개선하거나 반복되는 문장 틀을 바꿀 수 있다. 이는 원본 엔진의 ‘탐지 구절 외 수정 금지’를 넘어서는 서비스 확장이다.
- 한두 단어 교정이 여러 문장에 흩어진 것만으로 ‘폭넓은 재서술’에 성공했다고 보지 않는다. 실제 구문 재구성의 비중을 따로 평가한다.
- 문단 수·순서, 제목·목록, 각 문장의 정보·시간·조건·책임 주체는 유지한다. 초기 출시는 문장 경계도 유지한다. 문장 분할·병합·문단 재편집은 관계 검증을 보완하기 전에는 지원하지 않는다.
- 원문이 짧고 이미 적절하거나 대부분 보호 내용이면 변경 가능한 범위가 작을 수 있다. 이런 경우 이유를 안내하며 의미 없는 동의어 치환이나 사실 변경으로 수정량을 채우지 않는다.

## 4. 원본 규칙을 적용할 때의 중요한 제한

근거: `quick-rules.md`, `ai-tell-taxonomy.md`, `rewriting-playbook.md`.

- A-1 ‘~에 대해’, A-2 ‘~를 통해’, H-1 접속사 등에는 **문단 내 반복 횟수와 문맥 조건**이 있다. 매우 강하게라도 이 표현 자체를 오류로 몰아 전량 삭제하지 않는다. 일반적인 재서술과 규칙 위반 교정은 구분한다.
- F-4 명사화는 밀집 조건이 있다. 핵심 개념어인 ‘정확성’·‘안전성’ 등을 단순히 ‘-성’이라는 이유로 삭제하거나 다른 명사로 바꾸지 않는다.
- A-9의 피동→능동은 행위자가 원문에 있을 때만 한다. 행위자가 없는 문장에 ‘담당자’ 같은 주체를 새로 만들지 않는다.
- A-20/E-2 진행형 단순화는 시제·진행 상황이 달라지지 않을 때만 한다. ‘검토하고 있다’를 ‘검토했다’로 바꾸지 않는다.
- A-10/G-1/G-2의 완곡 정리는 확신 수준과 부정을 보존해야 한다. 특히 계약·협상 문장의 완곡은 입장 자체이므로 보호한다.
- G-3는 현재 룰북에 실증 부족/hold 표시가 있다. 강도 때문에 보류된 규칙을 활성화하지 않는다.
- C-2/C-9/C-10, E-1, I-4 등의 일부 처방은 목록 산문화·제목 변경·문장 병합·문장 이동을 요구한다. 이번 서비스 범위와 충돌하므로 해당 **구조 변경 처방은 모든 단계에서 제외**한다.
- D-4의 ‘구체 수치로 환원’은 원문에 그 수치가 있을 때만 가능하다. 강조 표현을 없애려고 없던 근거를 추가하지 않는다.
- 원본 playbook 일부 예시는 내용 앵커 보존이나 현재 서비스 구조 보존과 맞지 않을 수 있다. **서비스 보호 제약 → 최신 포함 룰북의 조건 → 단계별 편집 범위 → 예시** 순서로 적용하고 예시를 그대로 모방하지 않는다.
- `quick-rules.md`는 자동 생성 파일이다. 구현 시 파일을 직접 수정해 상위 강도를 끼워 넣지 않는다. 서비스 정책 모듈과 강도별 지침으로 분리한다.

## 5. 예시로 보는 지원 범위

다음은 모델 결과가 아니라 허용 범위를 설명하기 위한 작성 예시다. 단계별로 항상 다른 문자열이 나온다는 뜻이 아니다.

### 같은 원문의 국소 수정과 구문 재구성

원문: **이 방안은 강한 경쟁력을 가지고 있다.**

- 보통: `이 방안은 강한 경쟁력을 갖고 있다.`처럼 원래 구문을 살리는 교정이 가능하다.
- 중간: `이 방안은 경쟁력이 강하다.`처럼 형식적인 동사구를 정리할 수 있다.
- 강하게/매우 강하게: 같은 단문에서는 중간과 같은 결과가 적절할 수 있다. 네 단계의 차이를 만들려고 `경쟁력`을 `우위`로 바꾸거나 평가를 과장하지 않는다.

이 후보를 기존 문자 변경률 함수에 넣으면 첫 수정은 7.32%, 두 번째는 33.33%였다. 둘 다 같은 의미를 의도한 예시지만 두 번째는 기존 게이트에서 경고 대상이다. 짧은 문장에서는 작은 구문 전환도 높은 변경률이 될 수 있다.

### 매우 강하게는 여러 문장에서 실제 재구성

원문:

> 이번 검토에서 중요한 것은 자료의 정확성이다. 담당자는 자료의 정확성을 확인하기 위해 원본과 대조하는 작업을 수행한다. 검토 과정에 있어서 발견된 오류는 기록으로 남긴다.

가능한 매우 강하게의 방향:

> 자료의 정확성이 이번 검토에서 중요하다. 담당자는 원본과 대조하여 자료의 정확성을 확인한다. 검토 과정에서 오류를 발견하면 기록으로 남긴다.

세 문장 모두 표현을 바꾸되 검토·자료·정확성·담당자·원본·오류·기록이라는 내용과 문장 순서를 유지하는 예시다. 이 예시는 실제 강도별 모델·전체 게이트 평가 전의 후보이며 출시용 정답으로 고정하지 않는다.

### 모든 단계에서 금지

- `결과를 왜곡할 수 있다` → `결과를 왜곡한다`: 가능성을 사실로 바꿈.
- `가팀 12건, 나팀 20건` → `가팀 20건, 나팀 12건`: 숫자를 보존했어도 대상 관계를 바꿈.
- `민수는 사과, 지수는 배를 샀다` → `지수는 사과, 민수는 배를 샀다`: 이름과 명사가 남아 있어도 사실을 바꿈.
- `확인해야 한다` → `확인했다`: 의무를 완료 사실로 바꿈.
- `회의가 끝나면 자료를 보낸다` → `자료를 보내고 회의를 끝낸다`: 조건·순서를 바꿈.

## 6. ‘많이 변경’을 어떻게 확인할 것인가

별도 지표를 사용한다. 사용자가 선택한 강도를 숫자 변경률로 대체하지 않는다.

- **문장 수정률:** 원문 문장 중 최종 결과에서 실제로 바뀐 문장의 비율. 이미 엔진 P4에 유사한 보고 지표가 있지만 이동/분할과 정확한 대응을 구분하기 위해 문장 ID 기반 평가가 필요하다.
- **구문 재구성률:** 바뀐 문장 중 단순 띄어쓰기·쉼표·단어 치환을 넘어 어순/서술 구조가 달라진 비율. 초기에는 고정 검토표에 따른 사람이 판정하며 LLM 자가 점수를 객관 지표로 취급하지 않는다.
- **문자 변경률:** 기존 `metrics_v2.change_rate()`의 `1 - SequenceMatcher.ratio()`다. 바뀐 문장 수나 화면 노란색 비율과 다르다.
- **보호/복원 비율:** 넓게 고치려 했으나 보호 제약이나 검증으로 유지된 문장/청크를 별도로 기록한다.

매우 강하게의 출시 평가용 **재서술 가능성이 높은 합성 장문 표본**에서는 편집 가능한 문장의 약 70% 이상에서 실질적 표현 변화가 관측되는 것을 초기 목표로 삼는다. 이 수치는 사용자 입력에 적용하는 강제 할당량·약속·검증 게이트가 아니다. 문장별로 쉼표 하나만 바꿔 목표를 채우지 못하도록 구문 재구성 판정을 함께 한다. 보호 문장과 자연스러운 단문 중심의 표본에는 같은 목표를 적용하지 않는다.

32회 최소 실제 평가에서 매우 강하게가 보통/강하게와 계속 비슷한 국소 교정만 한다면, 넓은 변환 요구를 충족하지 못한 것으로 판정해 정책을 보완한다. 단계 이름만 추가하고 출시하지 않는다.

## 7. 현재 검증의 실측 한계와 구현 선행 조건

[6개 결정적 실험 결과](2026-09-10-strength-policy-probes.json)는 직접 작성한 후보를 현재 함수에 넣은 결과다. 모델 생성 결과나 서비스 전체 실행 성적이 아니다. 게이트와 복원기를 별도로 호출해 원인을 분리했다.

| 표본 | 문자 변경률 | 현재 검사 결과 | 의미 |
|---|---:|---|---|
| 국소 표현 교정 | 7.32% | accept | 정상 예시 |
| 같은 의미를 의도한 구문 압축 | 33.33% | 2차 기준 accept-with-warning | 의미가 유지돼도 구조 변경은 경고에 걸릴 수 있음 |
| 가능성 문장→단언+문장 분할 | 23.64% | 복원 보류 1건, 2차 기준 경고 수용 | 복원 보류 처리 필요 |
| 두 사람의 행위 대상 교환 | 9.52% | accept | 이름/명사 존재만으로 관계 보존을 검증할 수 없음 |
| 두 팀의 수치 교환 | 7.14% | 숫자 검사 및 전체 게이트 accept | 숫자 집합 보존만으로 대상-수치 관계를 보장하지 못함 |
| 자연스러운 문장 무수정 | 0% | accept | 무수정도 정상 결과 |

따라서 `skippedSentences` 재시도·롤백만으로 매우 강하게의 의미 보존이 충분히 검증됐다고 해서는 안 된다.

### 권장 구현 조건

1. 매우 강하게에서는 원문 문장/절별 ID와 원문 범위를 프로그램이 먼저 확정한다. 모델이 문장 ID를 새로 만들거나 재배열하지 못하게 하고, 대응되는 문장을 재서술해 받아 원문 순서로 조립한다. 현재 before/after compact 계약을 그대로 쓰는 경우에도 원문 범위가 어떤 문장에 속하는지 로컬에서 확인해야 한다.
2. 문장별 핵심 개념어·보호 구절을 유지한다. 자동 핵심어 판별이 확실한 의미 분석기는 아니므로 모델이 작성한 앵커 목록만으로 검증하지 않는다. 탐지 누락을 평가 표본에 포함한다.
3. 수치/날짜/이름·복수 주체·직접 인용·조건/부정/의무가 얽힌 고위험 문장은 초기 버전에서 보호 문장 또는 국소 수정으로 제한한다. 특히 한 문장 안 두 대상의 값이나 목적어 교환을 막는 회귀 테스트가 필요하다. **ID/순서 보존만으로 문장 내부 관계 오류가 해결되지는 않는다.**
4. 나머지 서술문은 문장 내부 구문을 폭넓게 재구성한다. 관계 보존 판정이 불확실한 결과는 재시도 후 원문으로 되돌린다. 현재 규칙만으로 모든 불확실성을 탐지할 수 있다는 보장은 하지 않는다.
5. 내용 앵커와 보호 정책을 우선하고, 원본의 국소 편집 제한은 very-strong의 검증된 재서술 구간에 한해 명시적으로 대체한다. 보통/파일/기존 클라이언트에는 정책이 새어 들어가지 않도록 한다.
6. 무조건 LLM 재검토 호출을 추가하지 않는다. 문장 ID·보호 검사로도 신뢰할 수 없는 범위를 넓히려면 별도 의미 평가 실험이 선행돼야 한다. 추가 검토 모델 역시 정확성 보증 수단으로 간주하지 않는다.

## 8. 50% 상한을 올려야 하는가

**많은 문장을 바꾸는 목표만으로 상한을 즉시 올릴 필요는 없다.** 여러 문장의 구문을 바꿔도 내용 어휘가 유지되면 전체 문자 변경률은 50% 미만일 수 있다. 반대로 짧은 문장은 한 문장만 바꿔도 상한에 가까워질 수 있다.

1차 연구·구현은 30% 경고/50% 중단을 유지하고 문장 수정률과 실제 구문 변화를 함께 측정한다. 상한 때문에 매우 강하게의 유효한 재서술이 계속 원문으로 복귀한다면 원인을 분리한다. 관계 보존 검증과 평가 데이터 없이 very-strong만 70~90%까지 허용하는 변경은 권장하지 않는다.

사용자가 원하는 광범위한 재서술과 기존 상한이 실제로 양립하지 않는다는 증거가 나오면, 매우 강하게 전용 검증 정책을 별도 설계 대상으로 보고한다. 메뉴 이름에 맞추기 위해 임계값을 조용히 완화하지 않는다.

## 9. 구현 계획에 반영할 결정

- 매우 강하게의 설명·평가 목표를 ‘글 전반의 많은 문장 실제 재서술’로 강화한다.
- 문장 내부 재구성과 문장 분할·병합을 구분한다. 넓은 적용은 전자를 글 전체에 적용하는 방식으로 시작한다.
- 기존 계획의 복원 보류 처리에 더해 내용 앵커 및 주체-행위/대상-수치 관계 보호를 선행 연구·검증 항목으로 추가한다.
- 높은 강도에서도 조건부 룰의 발동 조건과 hold 규칙을 무시하지 않는다.
- 프롬프트 4개와 UI 메뉴만으로 완료하지 않고 실제 문장 수정 범위·구문 재구성·의미 보존·복원 비율을 함께 평가한다.

아직 4단계 기능이나 위 보호 정책을 구현한 상태는 아니다. 다음 구현에서는 이 범위 정의를 평가 fixture와 강도별 프롬프트 계약으로 먼저 옮겨 검증해야 한다.
